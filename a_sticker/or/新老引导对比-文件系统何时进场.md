# 新老引导对比：文件系统何时进场

> **原材料（or/）**：AI 散文，配 [[自举链路-复位矢量到第一个进程]] 的对照稿。老式 = BIOS + MBR + 扇区；新式 = UEFI + GPT + ESP 上的 FAT。主线只回答一个问题：**「第一次读文件」发生在第几级、由谁完成。**

## 零、一句话

老式引导里，文件系统是**被逐级造出来**的：固件只会读扇区，bootloader 才第一次按名字找文件，剩下的由 initramfs 与 PID 1 补齐。新式引导里，固件自己就带一个文件系统（ESP 上的 FAT），所以**第一级就是读文件**。差别不在流程长短，而在第一次读文件的时刻提前了，且执行者从 bootloader 换成了固件。

## 一、并排

| 维度 | 老式（BIOS + MBR） | 新式（UEFI + GPT） |
|---|---|---|
| 固件接口 | `int 19h` 选设备 · `int 13h` 读扇区（CHS/LBA） | Boot services：块设备 + Simple File System + 内存映射 + 事件 |
| 第一级载体 | 512 B 扇区，末两字节 `0x55AA` | PE/COFF 可执行文件 `\EFI\BOOT\BOOTX64.EFI` |
| 分区表 | 446 B 代码 + 4 × 16 B 分区项，活动位 `0x80`，上限 2 TiB | 保护 MBR + 主/备 GPT 头 + 128 × 128 B 分区项，64 位 LBA |
| 谁提供 fs | bootloader 自带驱动（第一次读文件） | 固件内置 FAT 驱动（第一次读文件提前） |
| 内核入口状态 | 32 位保护模式（bzImage），内核自建页表 | 64 位长模式，PE 入口（EFI stub），固件已建映射 |
| 参数传递 | bootloader 拼内核命令行 | bootloader 拼命令行 + NVRAM 启动项（BootOrder） |
| 信任 | 无签名概念，任何能读出的 512 B 都会被跳进去 | Secure Boot：db/dbx 验签，shim → grub → kernel |
| fs 进场次数 | 4 次（bootloader / initramfs / 真根 / fstab） | 5 次（+ 固件读 ESP） |
| 典型失败 | `No bootable device` · `error: unknown filesystem.` | `Failed to load \EFI\BOOT\BOOTX64.EFI: Not Found` |

## 二、同一条链，两种走法

```
老式：
扇区(0x7C00) → MBR → VBR → bootloader[自带 ext4 驱动] → vmlinuz + initramfs
            → initramfs[内存 fs] → mount 真根 → switch_root → PID 1[fstab]

新式：
固件[FAT 驱动] → ESP:\EFI\BOOT\BOOTX64.EFI → bootloader(EFI 应用)
            → 仍从 fs 读 vmlinuz + initramfs → initramfs → mount 真根 → PID 1
```

两条路的后半段完全一样：**一旦内核跑起来，「文件系统怎么进场」就与固件无关了**。差别集中在固件懂不懂文件。

## 三、四次 vs 五次进场

| 阶段 | 老式 | 新式 |
|---|---|---|
| 0 固件 | 只读扇区，**没有 fs** | 读 ESP 上的 FAT → `\EFI\BOOT\BOOTX64.EFI` |
| 1 bootloader | 自备驱动读 `grub.cfg` / `vmlinuz` / `initramfs` | 同左（GRUB 此时是 EFI 应用） |
| 2 内核 | cpio 解到 rootfs（内存 fs） | 同左 |
| 3 initramfs | mount 真根 | 同左 |
| 4 PID 1 | 按 fstab 挂其余 | 同左 |

多出来的那一次是**最便宜的一次**：FAT 的目录项就是「名字 + 起始簇 + 长度」，固件不需要理解 ext4 的 inode、extent 树和日志。代价是把「谁的驱动算数」从 OS 手里拿走了一部分——ESP 的 FAT 由固件解释，不受内核 fs 驱动控制。

## 四、五个可观察的差别（各带例子）

### 1 分区表：`dos` 还是 `gpt`

```console
$ sudo fdisk -l /dev/sda
Disklabel type: dos          # 老式：上限 2 TiB，4 个主分区
$ sudo fdisk -l /dev/nvme0n1
Disklabel type: gpt          # 新式：128 项，64 位 LBA
```

GPT 盘上 `fdisk -l` 还会多出一行 `Disklabel type: gpt` 之外的 `Disk identifier`，并在 LBA 1 放 GPT 头、盘尾放备份头——头部自带 CRC32，损坏时固件/工具能直接判定「表坏了」，而 MBR 只有一个 `0x55AA`，内容错了也照样被跳进去。

### 2 `/boot` 的约束不同

- 老式：`/boot` 必须是 bootloader 认识的 fs。`grub-install /dev/sda` 把 `boot.img` 写进 MBR、把 `core.img`（含 ext4 驱动）写进 MBR 后的空隙，所以 `/boot` 换成 GRUB 不支持的格式，开机就是 `error: unknown filesystem.`。
- 新式：ESP 必须是 FAT（典型 100–512 MiB，挂 `/boot/efi`），`grub-install --target=x86_64-efi --efi-directory=/boot/efi` 把 GRUB 作为 EFI 应用放进去。内核与 initramfs 仍可留在 ext4 的 `/boot`，但此时读它们的是 GRUB 的驱动，而不是固件。

### 3 内核入口：谁已经在长模式

- 老式：`bzImage` 以 32 位保护模式入口启动，内核自己关中断、建页表、开 PAE、进长模式——自举里最脆的顺序段都在这里。
- 新式：`CONFIG_EFI_STUB=y` 的内核同时是一个 PE/COFF 应用，固件直接把它当 EFI 程序加载，进来就是 64 位长模式；`ExitBootServices` 之后固件退场，内核再建自己的页表。**同一份内核，两种入口。**

### 4 启动项存放在哪

```console
$ efibootmgr -v
BootCurrent: 0001
BootOrder: 0001,0000
Boot0001* Linux Boot Manager	HD(1,GPT,...)/\EFI\systemd\systemd-bootx64.efi
```

新式的 boot order 在 NVRAM 里，可以被 `efibootmgr -o` 改写，也可以被固件设置界面改；老式的顺序在固件设置里，或者干脆靠盘序。新式还留了一条兜底路径 `\EFI\BOOT\BOOTX64.EFI`——可移动介质靠它启动，不需要任何 NVRAM 项。

### 5 信任链

老式没有任何验签：能读出 512 B 并跳到 `0x7C00`，代码就跑了——bootkit 的门就在这里。新式在固件与 bootloader 之间插了一层签名检查：`shim`（微软 UEFI CA 签）→ `grub`（发行版密钥签，登记在 MokList/db）→ 内核。装第三方内核要 `mokutil --import`，否则固件直接拒绝加载——失败发生在「读文件」之前，因为固件连「这是不是一个可信的 PE 映像」都要先判。

## 五、同一台机的两种装法

```
老式：/dev/sda1 ext4 /boot    /dev/sda2 LVM  /
      grub-install /dev/sda

新式：/dev/nvme0n1p1 FAT32  /boot/efi    （ESP）
      /dev/nvme0n1p2 ext4   /boot
      /dev/nvme0n1p3 LVM    /
      grub-install --target=x86_64-efi --efi-directory=/boot/efi
```

迁移时的第一个症状通常不是引导失败，而是**分区工具拒绝**：MBR 盘超过 2 TiB 的部分无法寻址。换 GPT 要重写分区表（`sgdisk -g` / `gdisk` 转换），同时决定走 UEFI（需要 ESP）还是留在 legacy（需要 MBR 空隙装 `core.img`）。

## 六、边界与中间态

- **UEFI + CSM**：固件模拟 BIOS 服务，能引导 MBR 老盘——这是两种方式的拼接，不是第三种方式。
- **UEFI 仍可让 bootloader 读 fs**：新式只是把「第一次读文件」提前，后面几次进场与老式相同；所以「新式 = 内核直接读根」是错的。
- **虚拟机**：OVMF 给虚拟机一份 UEFI 固件，进场次数与真机一致；容器没有引导，直接继承宿主 mount namespace，两者都不属于这条链路。
- **共同的本质**：两条路都要一次「固件 → 内核」的协议交接，都是先建能力、后交权；顺序错了，两条路都会以 panic 收场，只是报错的位置不同——老式常见在 `unknown filesystem`（bootloader 那一级），新式常见在 `Failed to load image`（固件那一级）。
