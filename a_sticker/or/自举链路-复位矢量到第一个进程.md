# 自举链路：复位矢量 → 第一个进程

> **原材料（or/）**：AI 散文，供你消化成卡。链路与命题是你已接受的版本；这一版补上原先缺的**文件系统段**，其余不动。

## 一、完整链路

```
复位 → POST → 固件按 boot order 找设备
  → LBA 0 读进 0x7C00           BIOS int 13h：只认扇区，不认文件
  → MBR → 活动分区 VBR → bootloader
  → bootloader 自带 fs 驱动：grub.cfg → vmlinuz + initramfs
  → 切保护模式 / 长模式 → 跳内核
  → 解压 → initramfs(cpio) 解到 rootfs（ramfs/tmpfs）
  → exec /init（第一个用户进程，PID 1）
  → 加载 fs 驱动 → mount 真根 → switch_root
  → exec /sbin/init（仍是 PID 1）
  → systemd 按 fstab 挂其余 fs → 之后被中断驱动
```

分界：**第一扇区之前没有文件，只有扇区和一条跳转约定**；之后每一级都在为「读文件」加一层能力。

## 二、文件系统出现五次

| # | 阶段 | 谁解析 fs | 拿到什么 |
|---|---|---|---|
| 1 | UEFI 固件 | 固件内置 FAT 驱动 | ESP 上的 `BOOTX64.EFI` |
| 2 | bootloader | GRUB 自带驱动 | `grub.cfg` · `vmlinuz` · `initramfs.img` |
| 3 | 内核 | cpio 解包，无磁盘 fs | rootfs（ramfs/tmpfs） |
| 4 | initramfs userland | fs 模块 + mount | 真根 `/` |
| 5 | PID 1 | [[VFS (Virtual File System)]] | fstab 上的其余挂载点 |

## 三、逐段

### 0 固件：只有扇区

- BIOS：`int 19h` 找启动设备，`int 13h` 读扇区（CHS/LBA）；没有 fs 概念。
- UEFI：固件自带 FAT 驱动，直接读 ESP 的 `/EFI/BOOT/BOOTX64.EFI` —— 第一次按**文件**启动。

### 1 bootloader：被逼着实现 fs

- 要读 `/boot/grub/grub.cfg`、`vmlinuz`、`initramfs.img`，必须先解析磁盘格式。
- GRUB 内置 ext2/3/4 · XFS · Btrfs · FAT · NTFS（只读）模块 ⇒ 同一格式由**第二份实现**读懂。
- 约束：`/boot` 必须是 bootloader 认识的 fs；全盘 LUKS 时 `/boot` 通常留明文，或 GRUB 自带 crypto。

### 2 内核：initramfs 是内存 fs

- kernel image 内嵌 cpio（可压缩）；没有 initramfs 时内核直接 mount root。
- 有：解到 rootfs（ramfs/tmpfs）—— 跑用户态**不需要磁盘 fs**；里面是 fs 模块 + udev + mount 工具。
- 鸡与蛋：根 fs 的驱动可能躺在根 fs 上 ⇒ 用内存 fs 打破循环。

### 3 mount 真根

- `root=UUID=… rootfstype=… ro` 来自 `/proc/cmdline`（bootloader 传参）；或 initramfs 里 udev 按 UUID/LABEL 找。
- 读 [[Superblock|超级块]] → 根 inode → [[Dentry|dentry]] 树；失败 = `VFS: Unable to mount root fs` → panic。
- `switch_root` / `pivot_root`：真根挂到 `/`，旧 rootfs 卸载。

### 4 exec init

- **补正**：第一个用户进程出现在 initramfs 阶段——内核 `kernel_init` exec `/init`，PID 1 从此是用户态；无 initramfs 时才是直接 exec `/sbin/init`。
- `switch_root` 后再 exec `/sbin/init`，PID 1 不变；PID 0 = idle，PID 2 = kthreadd。
- exec 前 fd 0/1/2 已接 `/dev/console` ⇒ 第一个进程开局就有三个 [[Struct File|file]]。
- 之后 systemd 按 fstab 挂其余 fs（`local-fs.target`），mount namespace 建立，inode/dentry 缓存开始工作。

## 四、原先的四处修正（不变）

1. **主板不加载 BIOS**：固件本就在 ROM/SPI flash 里；主板只是按硬连线约定把 PC 置到复位矢量。
2. **POST 在找启动设备之前**：复位 → POST → 按启动顺序找设备 → 读第一个扇区到 0x7C00 → 跳转。
3. **三态，不是两态**：实模式 →（bootloader 设 CR0.PE）保护模式（未开分页，线性 = 物理）→（内核建页表、设 CR0.PG）分页。
4. **顺序与术语**：建临时 IDT/GDT → 建页表 → 开分页 → 建最终 IDT → start_kernel；实模式那张叫 **IVT**（0x0000，4 字节/项），之后叫 **IDT**（IDTR 指向，8/16 字节/项）。

## 五、原先缺的三条边（不变）

1. **GDT**：保护模式的前提。
2. **开分页前关中断（CLI）**：IDT 未建好时来中断就跳飞。
3. **恒等映射**：设 `CR0.PG` 那条指令的物理地址必须先映射到自己的虚拟地址。
4. 附：x86_64 长模式要求先开 PAE 分页 —— 分页不是可选优化。

## 六、核心命题（不变）

**自举 = 机器用一条硬连线约定启动自己，然后把「改写解释规则的权力」逐级移交给软件。**

三层意义：

1. **可见性刚好够加载下一级**：复位矢量只够一条指令 → 实模式 1 MB → 保护模式 4 GB 线性 → 分页任意虚拟地址 → 长模式 64 位。
2. **特权从「无人拥有」到「OS 拥有」= 元层诞生**：连「什么算程序、地址怎么解释」都能被存储的位串改变。
3. **顺序即安全**：先建合同、后开通道；失败几乎全是顺序错。

**文件系统补进后**：自举还要加一条**解释链**——固件懂扇区 → bootloader 懂 fs → 内核懂 VFS → initramfs 懂 mount。同一磁盘格式必须被两份代码读（bootloader 驱动 + 内核驱动），**格式 = 实现之间的合同**。

**合流点**：距离链（ROM → 磁盘 → 内存 → Cache → 寄存器）与能力链（可见性 + 特权）在第一个用户进程处合流——两级名字（虚拟/物理）与两级权限（用户/内核）都已就位，OS 退居幕后，只等中断唤醒。

**边界**：

- UEFI 把移交前置（固件已给 FAT、保护模式/长模式/分页），级数变少、本质不变。
- 虚拟机/容器没有真复位：第一级约定换成 hypervisor 的 ABI；容器直接继承宿主 mount namespace，没有 fs 自举。
- 移交**不彻底**：SMM 与 hypervisor 保留后门特权。
- 「通用性由此实现」要限定：自举只是让它**可被重新定义**的那一环。
