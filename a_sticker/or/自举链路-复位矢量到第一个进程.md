# 自举链路：老式引导里文件系统如何一路进场

> **原材料（or/）**：AI 散文，供你消化成卡。**主线 = 老式引导（BIOS + MBR）中文件系统的四次进场**；链路、四处修正、三条边与核心命题仍是你已接受的版本，只换了视角与顺序。

## 零、主线一句话

**老式引导的前半段没有文件，只有扇区。** 固件不会「打开文件」，它只会「读第 N 个扇区、看最后两个字节是不是 `0x55AA`、跳过去」。所以「读文件」这项能力必须由后面每一级自己带上：bootloader 自带 fs 驱动，内核用内存 fs 打破鸡蛋循环，initramfs 里的 mount 把真根接上，PID 1 再把剩下的挂载点补齐。文件系统不是启动的前提，而是启动过程里被逐级**造出来**的东西。

## 一、链路总图（标出 fs 的位置）

```
复位 → POST → 固件按 boot order 找设备
  → LBA 0 读进 0x7C00            BIOS int 13h：只认扇区，不认文件   ← fs 尚不存在
  → MBR → 活动分区 VBR → bootloader
  → bootloader 自带 fs 驱动：grub.cfg → vmlinuz + initramfs        ← 第 1 次进场
  → 切保护模式 / 长模式 → 跳内核
  → 解压 → initramfs(cpio) 解到 rootfs（ramfs/tmpfs）              ← 第 2 次进场（内存 fs）
  → exec /init（第一个用户进程，PID 1）
  → 加载 fs 驱动 → mount 真根 → switch_root                        ← 第 3 次进场（真根）
  → exec /sbin/init（仍是 PID 1）
  → systemd 按 fstab 挂其余 fs → 之后被中断驱动                     ← 第 4 次进场
```

分界：**第一扇区之前没有文件，只有扇区和一条跳转约定**；之后每一级都在为「读文件」加一层能力。

## 二、主线：文件系统四次进场

| # | 谁在读 | 用什么读 | 拿到什么 | 失败时看到什么 |
|---|---|---|---|---|
| 1 | bootloader | 自带磁盘 fs 驱动（ext2/3/4 · XFS · Btrfs · FAT · NTFS，只读） | `/boot/grub/grub.cfg`、`vmlinuz`、`initramfs.img` | `error: unknown filesystem.` |
| 2 | 内核 | cpio 解包，不需要磁盘 fs | rootfs（ramfs/tmpfs） | 无此步时直接 mount 根，失败即 panic |
| 3 | initramfs userland | fs 模块 + udev + `mount` | 真根 `/` | `VFS: Unable to mount root fs` |
| 4 | PID 1 | [[VFS (Virtual File System)]] + fstab | 其余挂载点 | emergency mode / degraded |

四次进场的共同点：**同一份磁盘格式，被不止一份代码解析**——bootloader 的 ext4 驱动与内核的 ext4 是同一种格式的两个实现。格式就是实现之间的合同。

## 三、逐段

### 1 固件：扇区是唯一接口（fs 尚未存在）

- BIOS：`int 19h` 找启动设备，`int 13h` 读扇区（CHS/LBA）；没有 fs 概念，也就没有「文件不存在」这种错误——只有「扇区读不出」和「签名不对」。
- 流程是固定顺序：复位 → POST → 按 boot order 找设备 → 读第一个扇区到 `0x7C00` → 检查末两字节 `0x55AA` → 跳转。
- 例：`dd if=/dev/zero of=/dev/sda bs=512 count=1` 抹掉第一个扇区后重启，固件报 `No bootable device`——它不是「找不到系统」，是「找不到一条可跳的约定」，于是试 boot order 的下一项。
- 修正（不变）：**主板不加载 BIOS**——固件本就在 ROM/SPI flash 里，主板只是按硬连线约定把 PC 置到复位矢量。

### 2 MBR → VBR：分区表冒充目录

- 第一个扇区的布局：`446 B` 引导代码 + `4 × 16 B` 分区项 + `0x55AA`，活动分区用 `0x80` 标记；超过 4 个分区就得走扩展分区链。
- 从 fs 视角看，分区表是**一个没有 inode 的目录**：它给的是 extent（起始 LBA + 扇区数），不是名字到数据的映射。真正「按名字找文件」的能力，下一级才有。
- 例：`fdisk -l` 里 `Disklabel type: dos`、`Start 2048`（1 MiB 对齐）、`Sector size (logical/physical): 512/4096`；分区项本身可直接看：`dd if=/dev/sda bs=1 skip=446 count=64 | xxd`。
- 硬约束：4 个主分区、最大 `2 TiB`（`2³²` 个 512 B 扇区）——这就是 MBR 盘装大容量盘时必须换 GPT 的原因。

### 3 bootloader：第一次「读文件」，被逼实现 fs

- 要读 `/boot/grub/grub.cfg`、`vmlinuz`、`initramfs.img`，就必须先解析磁盘格式。GRUB legacy 把这一步拆成三段正是被空间逼的：`stage1`（446 B，只够加载下一段）→ `stage1_5`（fs 驱动，塞进 MBR 与第一个分区之间的空隙）→ `stage2`（真正读配置与内核）。GRUB 2 的 `core.img` 是同一角色的合并版。
- 内置只读驱动：ext2/3/4 · XFS · Btrfs · FAT · NTFS。同一 ext4，内核里另有一份实现。
- 约束：`/boot` 必须是 bootloader 认识的 fs。例：`/boot` 放进 GRUB 不支持的存储池 → 开机即 `error: unknown filesystem.`；全盘 LUKS 时 `/boot` 通常留明文，或由 GRUB 自带 `cryptodisk` 解密。
- 紧接其后的「地址能力」移交（bootloader 切保护模式；内核关中断、建页表、进长模式）是主线外的边，见第四节。

### 4 initramfs：内存 fs 打破鸡蛋循环

- 内核 image 内嵌 cpio（可压缩）；没有 initramfs 时内核直接 mount root，有就先解到 rootfs（ramfs/tmpfs）。
- 为什么要这一步：**根 fs 的驱动可能躺在根 fs 上**（LVM/LUKS/RAID 模块在 `/lib/modules`，`/lib/modules` 在根上）。用内存 fs 跑起一个最小用户态，循环就断了。
- 这个阶段跑用户态**不需要磁盘 fs**——rootfs 是内存，`/init` 是 cpio 里解出来的文件。
- 例：`lsinitramfs /boot/initramfs-$(uname -r).img | grep -m3 ext4` 能看到 `ext4.ko` 就在 initramfs 里；`root=UUID=… rootfstype=ext4 ro` 是 bootloader 通过 `/proc/cmdline` 传进来的。

### 5 mount 真根：文件树接上真设备

- 读 [[Superblock|超级块]] → 根 inode → [[Dentry|dentry]] 树，VFS 的三层对象（superblock / inode / dentry）此时全部就位。
- `switch_root` / `pivot_root`：真根挂到 `/`，旧 rootfs 卸载。例：`switch_root /sysroot /sbin/init`。
- 失败的样子：`VFS: Unable to mount root fs on unknown-block(0,0)` → panic。`unknown-block(0,0)` 的意思是「连设备号都没解析出来」，通常是 `root=` 指错，或驱动没进 initramfs——不是文件系统损坏。

### 6 exec init：第一个进程开局就有三个 file

- **第一个用户进程出现在 initramfs 阶段**：内核 `kernel_init` exec `/init`，PID 1 从此是用户态；没有 initramfs 时才是直接 exec `/sbin/init`。
- `switch_root` 之后再 exec `/sbin/init`，PID 1 不变；PID 0 = idle，PID 2 = kthreadd。
- exec 前 fd 0/1/2 已接 `/dev/console` ⇒ 第一个进程开局就有三个 [[Struct File|file]]。
- 之后 systemd 按 fstab 挂其余 fs（`local-fs.target`），mount namespace 建立，inode/dentry 缓存开始工作。例：`systemd-analyze blame | grep '\.mount'` 列出的就是这次进场的产物。

## 四、主线之外的边（原四处修正与三条边，不变）

1. **主板不加载 BIOS**：固件本就在 ROM/SPI flash 里；主板只是按硬连线约定把 PC 置到复位矢量。
2. **POST 在找启动设备之前**：复位 → POST → 按启动顺序找设备 → 读第一个扇区到 0x7C00 → 跳转。
3. **三态，不是两态**：实模式 →（bootloader 设 CR0.PE）保护模式（未开分页，线性 = 物理）→（内核建页表、设 CR0.PG）分页。
4. **顺序与术语**：建临时 IDT/GDT → 建页表 → 开分页 → 建最终 IDT → `start_kernel`；实模式那张叫 **IVT**（0x0000，4 字节/项），之后叫 **IDT**（IDTR 指向，8/16 字节/项）。
5. **GDT**：保护模式的前提。
6. **开分页前关中断（CLI）**：IDT 未建好时来中断就跳飞。
7. **恒等映射**：设 `CR0.PG` 那条指令的物理地址必须先映射到自己的虚拟地址。
8. 附：x86_64 长模式要求先开 PAE 分页 —— 分页不是可选优化。

## 五、核心命题（不变）

**自举 = 机器用一条硬连线约定启动自己，然后把「改写解释规则的权力」逐级移交给软件。**

三层意义：

1. **可见性刚好够加载下一级**：复位矢量只够一条指令 → 实模式 1 MB → 保护模式 4 GB 线性 → 分页任意虚拟地址 → 长模式 64 位。
2. **特权从「无人拥有」到「OS 拥有」= 元层诞生**：连「什么算程序、地址怎么解释」都能被存储的位串改变。
3. **顺序即安全**：先建合同、后开通道；失败几乎全是顺序错。

**文件系统补进后**，自举还要加一条**解释链**——固件懂扇区 → bootloader 懂 fs → 内核懂 VFS → initramfs 懂 mount。同一磁盘格式必须被两份代码读（bootloader 驱动 + 内核驱动），**格式 = 实现之间的合同**。

**合流点**：距离链（ROM → 磁盘 → 内存 → Cache → 寄存器）与能力链（可见性 + 特权）在第一个用户进程处合流——两级名字（虚拟/物理）与两级权限（用户/内核）都已就位，OS 退居幕后，只等中断唤醒。

**边界**：

- 虚拟机/容器没有真复位：第一级约定换成 hypervisor 的 ABI；容器直接继承宿主 mount namespace，没有 fs 自举。
- 移交**不彻底**：SMM 与 hypervisor 保留后门特权。
- 「通用性由此实现」要限定：自举只是让它**可被重新定义**的那一环。
- 新式引导（UEFI + GPT）把固件那一步也变成「读文件」，进场次数与移交位置都变了——见 [[新老引导对比-文件系统何时进场]]。
