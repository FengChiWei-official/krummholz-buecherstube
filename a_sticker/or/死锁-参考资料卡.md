# 死锁：四个必要条件与三种处理

> **口径 / 用法**：408 与汤小丹《计算机操作系统》的术语与判据。一篇覆盖「四条件 + 预防 / 避免 / 检测解除」。自测时只看表格左列，能复述右列即过；卡住回教材对应章。
> **一句话骨架**：死锁是「各自持有、互相等待，无外力不散」。四条件同时成立才**可能**死锁；三种处理分别落在事前改规则（预防）、事前试算（避免）、事后发现并恢复（检测 / 解除）。

## 一、四个必要条件

四个条件**同时成立**是死锁的**必要条件**：缺一不可能死锁；全齐也不一定死锁——还需要恰当的申请时序。这也是「预防只要破坏任意一个」的根据。

| 条件 | 精确表述 | 判定要点 |
|---|---|---|
| 互斥 | 资源在任一时刻只能被一个进程占用，其他请求者必须等待 | 只对**不可共享资源**（临界资源：打印机、磁带机、被写的文件）成立；只读文件、可重入代码不构成 |
| 请求和保持（占有并等待） | 进程已持有至少一个资源，又请求新资源并被阻塞，且**不释放**已持有资源 | 两个动作缺一不可：持有 + 请求被拒后仍持有 |
| 不可剥夺（不剥夺） | 资源只能由持有者**主动释放**，OS 不能强行收回；进程推进受阻时也不放已占资源 | 关键在「无人能抢」，不是「没人愿意放」 |
| 循环等待（环路等待） | 存在进程集合 {P₀,…,Pₙ}：P₀ 等 P₁ 占的资源，P₁ 等 P₂ 占的资源，…，Pₙ 等 P₀ 占的资源 | 等价于资源分配图里一条闭环；单实例时环 ⟺ 死锁，多实例时环只是必要非充分 |

**强度差别（高频判定）**：每类资源只有一个实例时，「资源分配图有环」与「死锁」等价；同类资源有多个实例时，环可能存在而等待最终被其他进程的释放打破，所以环只是死锁的必要条件。四个条件本身也一样：必要，不充分。

### 例子：一台打印机、一台磁带机

R1 = 打印机（1 个），R2 = 磁带机（1 个）。P0 已拿到打印机、又要磁带机；P1 已拿到磁带机、又要打印机：

```
             请求 R2
      P0 ───────────────▶ R2
      ▲                   │
      │ 分配 R1           │ 分配 R2
      │                   ▼
      R1 ◀─────────────── P1
             请求 R1
```

环：P0 → R2 → P1 → R1 → P0。四个条件同时成立：

| 条件 | 图上对应 |
|---|---|
| 互斥 | R1、R2 各 1 个实例，同一时刻只能给一个进程 |
| 请求和保持 | P0 已持有 R1，请求 R2 被拒后仍握着 R1 |
| 不可剥夺 | OS 不会把 R1 从 P0 手里抢给 P1 |
| 循环等待 | 沿箭头走一圈回到 P0 |

单实例时环就是死锁。若 R1 有 2 个实例（P0 持 1，另一个被一个**没有任何请求**的 P2 持着），同一张图上的环**不再**是死锁：P2 完成后释放 R1，P1 的请求随即得到满足，环被打破。这个反例在 §2.3 用化简法重走。

## 二、三种处理

| 策略 | 介入时点 | 一句话 | 对四个条件 |
|---|---|---|---|
| 死锁预防 | 运行前定规则 | 破坏至少一个必要条件 | 使条件**不成立** |
| 死锁避免 | 每次分配前 | 试算分配后是否仍安全，不安全就让请求等待 | 不破坏，允许成立 |
| 死锁检测与解除 | 死锁可能已发生之后 | 用图 / 矩阵找出死锁，再剥夺资源或撤销进程 | 允许全部成立，也允许真的死锁 |

### 2.1 预防：静态破坏必要条件

| 破坏的条件 | 方法 | 代价 / 限制 |
|---|---|---|
| 互斥 | 把独占设备改造成共享设备：SPOOLing 技术把打印机虚拟成可排队的共享设备 | 只适用于可虚拟化或天然可共享的资源；临界资源的互斥是本质属性，一般破坏不了，所以这条最少用 |
| 请求和保持 | ① 静态分配：运行前一次性申请全部资源，运行中不再申请；② 只允许在**未持有任何资源**时申请 | 资源利用率低；大需求进程可能永远凑不齐而饥饿；编程受约束 |
| 不可剥夺 | 请求新资源失败时，必须释放已持有的全部资源，以后重新申请；或由 OS 直接抢占（如内存页换出） | 反复申请—释放，前面工作作废；只适用于状态可保存 / 恢复的资源（CPU 现场、内存），打印机等不可恢复 |
| 循环等待 | 资源有序分配法：给每类资源全局编号，进程只能按编号**递增**顺序申请 | 编号限制新设备加入；申请顺序被锁死，灵活性差，仍可能低效 |

四个破坏各一个具体例子：

- **互斥**：3 台打印机 → 1 个 SPOOLing 输出队列。进程申请的是「打印任务」，不是设备本身，设备由系统串行驱动。
- **请求和保持**：进程需要「打印机 + 2 个缓冲区」→ 启动时一次申请 3 个；或规定只持有打印机时不许再申请缓冲区（先释放再申请）。
- **不可剥夺**：进程已占 2 页内存、请求第 3 页失败 → 把 2 页换出到磁盘（保存现场），清空占用后重新排队。
- **循环等待**：资源编号 打印机=1、磁带机=2、磁盘=3。持有磁带机（2）的进程不许再申请打印机（1）——要按 1→2→3 递增，环就不可能闭合。

共同代价：实现简单、无运行时计算，但资源利用率与并发度在三种策略里最低。

### 2.2 避免：动态试算安全状态

**安全状态 / 安全序列**：系统能按某个顺序 ⟨P₁,…,Pₙ⟩ 为每个进程分配其**剩余最大需求**，使每个进程都能完成；这样的顺序叫安全序列，存在安全序列即安全状态。

- 安全状态 ⇒ 一定无死锁。
- 不安全状态 ⇏ 已死锁：只是**可能**死锁，取决于实际申请时序。

**银行家算法的数据结构**（n 个进程、m 类资源）：

- `Available[m]`：当前可用资源
- `Max[n][m]`：每个进程声明的最大需求（必须**预知**）
- `Allocation[n][m]`：已分配
- `Need[n][m] = Max − Allocation`：尚需

**安全性算法**（判断当前状态是否安全，O(n²m)）：

1. `Work = Available`，`Finish[i] = false`
2. 找 `Finish[i] = false` 且 `Need[i] ≤ Work` 的进程 i；找不到转第 4 步
3. `Work += Allocation[i]`，`Finish[i] = true`，回到第 2 步
4. 若全部 `Finish = true` → 安全，找到的顺序就是安全序列；否则不安全

**请求处理**（进程 Pᵢ 请求 `Requestᵢ`）：

1. `Requestᵢ ≤ Needᵢ`，否则请求非法（超过自己声明的上限）
2. `Requestᵢ ≤ Available`，否则 Pᵢ 等待
3. 试探分配：`Available −= Requestᵢ`，`Allocationᵢ += Requestᵢ`，`Needᵢ −= Requestᵢ`
4. 跑安全性算法：安全 → 正式分配；不安全 → 撤销试探，Pᵢ 等待

**算例**（两类资源 A、B，`Available = (1,3)`）：

| 进程 | Max | Allocation | Need |
|---|---|---|---|
| P₀ | (2,4) | (1,2) | (1,2) |
| P₁ | (0,2) | (0,1) | (0,1) |
| P₂ | (3,1) | (1,0) | (2,1) |

当前安全，序列 ⟨P₀,P₁,P₂⟩：Work (1,3) → 满足 P₀ → (2,5) → 满足 P₁ → (2,6) → 满足 P₂ → (3,6)。

P₂ 请求 (1,0)：`Request ≤ Need₂`、`Request ≤ Available` 都成立，试分配后 `Available = (0,3)`、`Need₂ = (1,1)`。此时 Work (0,3) 能满足 P₁ → (0,4)，但 P₀ 需要 1 个 A、P₂ 需要 1 个 A，A 已为 0 → 无安全序列 → **拒绝**该请求。

```
试分配: Available = (0,3)
  P1: Need (0,1) <= (0,3)  OK  -> 回收 Alloc (0,1), Work = (0,4)
  P0: Need (1,2) 需要 1 个 A, 现有 0  -> 卡住
  P2: Need (1,1) 需要 1 个 A, 现有 0  -> 卡住
  => 没有可完成的进程, 无安全序列, 撤销试分配, P2 等待
```

**代价**：每个进程必须事先声明最大需求（实际很难）；每次请求都要 O(n²m) 试算；判据保守，资源利用率低于事后检测。它**不破坏任何必要条件**——这正是与预防的分界。

### 2.3 检测与解除：允许发生，事后处理

检测时机两选一：每次资源请求 / 分配时检测（实时，开销大），或定时检测、在 CPU 利用率下降时检测（延迟）。

**资源分配图**：圆圈 = 进程，方框 = 资源类，方框内圆点 = 实例；请求边 Pᵢ→Rⱼ，分配边 Rⱼ→Pᵢ。

- 无环 → 一定无死锁（充分判据）。
- 有环：单实例 → 死锁；多实例 → 只是必要条件。

**死锁定理**：状态 S 为死锁状态 ⟺ S 的资源分配图**不可完全简化**。

化简：反复找一个「请求边都能被满足且未孤立」的进程结点，消去它的全部请求边与分配边，使之成为孤立结点。能消去所有边 → 无死锁；消不完 → 剩下的进程就是死锁进程。

**例：图上有环，却没有死锁**（沿用 §一 的图）

单实例版（R1、R2 各 1 个）：P0 等 R2、P1 等 R1，两条请求边都无实例可满足 → 找不到可化简的进程 → 不可完全化简 → 两个进程都是死锁进程。

多实例版：R1 两个实例，P0 持 1、P2 持 1（P2 无任何请求）；R2 一个实例，P1 持 1。环仍是 P0 → R2 → P1 → R1 → P0：

```
资源: R1 有 P0、P2 两个持有者      R2 只有 P1 持有
请求: P0 -> R2                     P1 -> R1

      P0 ──请求 R2──▶ R2 ──分配──▶ P1
      ▲                            │
      │ 分配 R1                    │ 请求 R1
      │                            ▼
      R1 ◀─────────────────────────┘
             P2 也占着 R1 的一个实例, 但没有请求
```

```
1. P2: 有分配边、无请求边 => 既不阻塞又非孤立
   消去 R1 -> P2  =>  P2 孤立, R1 出现空闲实例
2. P1 的请求 R1 可满足 => 消去 P1 的两条边
   =>  P1 孤立, R2 被释放
3. P0 的请求 R2 可满足 => 消去 P0 的边 => P0 孤立
4. 所有边消完 => 可完全化简 => 不是死锁
```

判据是「能否化简」，不是「图上有没有环」：单实例时两者恰好等价，多实例时环只是必要条件。

**多实例的矩阵检测**（与银行家算法形似，但用**当前请求**而非最大需求）：`Work = Available`，`Finish = false`；反复找 `Finish = false` 且 `Requestᵢ ≤ Work` 的进程，`Work += Allocationᵢ`；循环结束后仍为 false 的进程即死锁进程。区别在判据：检测问「现在是否已经卡死」，避免问「分配后是否还安全」。

**等待图**：单实例专用。Pᵢ→Pⱼ 表示 Pᵢ 等待 Pⱼ 占有的资源；有环 ⟺ 死锁。它是资源分配图去掉资源结点后的压缩版。§一 的图压过来只剩两条边：

```
P0 等 R2, 而 R2 在 P1 手里   =>  P0 ──▶ P1
P1 等 R1, 而 R1 在 P0 手里   =>  P1 ──▶ P0
有环 P0 ⇄ P1  =>  死锁
```

**解除**：

| 手段 | 做法 | 代价 / 风险 |
|---|---|---|
| 资源剥夺（抢占） | 从死锁进程强行取走资源，交给其他进程 | 要选牺牲者；被剥夺进程必须能回滚到安全点；同一进程可能反复被剥夺 → 饥饿（把被剥夺次数计入代价） |
| 撤销进程 | 撤销全部死锁进程（最彻底、最贵），或按代价从小到大逐个撤销直到死锁消失 | 代价度量：优先级、已运行时间、剩余时间、已占资源、交互式还是批处理 |
| 进程回退 | 设检查点，让进程回退到死锁发生前的状态并释放资源 | 需要 checkpoint / rollback 机制，实现复杂 |

三个例子（对应上面三种手段）：

- **剥夺**：P0 占着 2 个缓冲区死等 → 强行收回 1 个交给 P1；P0 必须能回到「申请缓冲区之前」的检查点，否则已写数据作废。若 P0 每次都被选为牺牲者，它会一直推进不了——这就是代价列里的饥饿。
- **撤销**：选「优先级最低、已运行时间最短」的 P1 撤销，释放它持有的 R2，环当场断开；若撤销一个还不够，按代价从小到大继续撤销。
- **回退**：P0 在申请 R2 前设过检查点，回退到该点并释放 R1，系统回到环形成之前的状态。

代价 = 检测开销 + 恢复损失；但正常运行时几乎没有并发限制，资源利用率三种策略里最高。实践中的第四种选择是「不处理」（鸵鸟策略），交给用户重启——UNIX / Linux 的常见做法。

## 三、三种处理对比

| | 预防 | 避免 | 检测与解除 |
|---|---|---|---|
| 介入时点 | 运行前，静态规则 | 运行中，每次分配前 | 事后 |
| 对四条件 | 破坏至少一个 | 不破坏，允许成立 | 允许全部成立并真的死锁 |
| 判据 | 规则本身 | 安全序列 / 银行家算法 | 分配图化简 / 等待图找环 |
| 资源利用率 | 最低 | 中 | 最高 |
| 主要代价 | 并发度低、可能饥饿 | 需预知 Max、每次请求 O(n²m) | 检测开销 + 恢复损失 |
| 适用 | 资源少、规则固定的系统 | 资源类少、需求可预知 | 通用 OS，配合鸵鸟策略 |

## 四、易错点（判分口径）

- 四条件是**必要不充分**：「同时成立」≠「一定死锁」。
- 单实例：资源分配图有环 ⟺ 死锁；多实例：有环只是必要非充分。
- 安全状态 ⇒ 无死锁；不安全状态 ≠ 已死锁。
- 银行家算法属于**避免**，不是预防：它不破坏任何条件，只保证不进入不安全状态。
- 检测算法用「当前请求 Request」，银行家算法用「最大需求 Need / 尚需」——形似而判据不同。
- 死锁 vs 饥饿：死锁有环、互相等待、无外力不散；饥饿是长期得不到调度，但系统其他部分仍在推进。
- 最小资源数：n 个进程、每个最多需 k 个同类资源时，保证不死锁的最少资源数 `m ≥ n(k−1) + 1`（最坏情形每个进程先各持 k−1 个）。例：5 个进程、每个最多要 3 台打印机 → `m ≥ 5×2+1 = 11` 台。
- 破坏互斥只对可共享 / 可虚拟化资源可行；破坏不可剥夺只对状态可保存 / 恢复的资源可行。

## 五、速记

- 四条件：互斥、请求保持、不剥夺、循环等待。
- 三处理：预防改规则 / 避免试算安全 / 检测化简图再剥夺或撤销。
- 预防四刀：共享化（破互斥）、一次要够（破请求保持）、能抢（破不剥夺）、按序要（破循环等待）。
